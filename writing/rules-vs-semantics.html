Only the semantics go to the model

Jack Wright · August 2026

The instinct on any document-reconciliation problem is to hand the whole judgment to a model: here is the agreement, here is our template, tell me what's missing. It works well enough in a demo to be dangerous.

The failure isn't accuracy. It's that you cannot answer the only question that matters in review: why did it decide that? The answer is a prompt. Nobody can audit a prompt, nobody can unit-test one, and when a reviewer disagrees with one output your only lever is to reword the instructions and re-run everything downstream.

The split

Every decision in a reconciliation engine falls into one of two buckets.

  • Rules you can write down unambiguously. Which side's number wins when both specify one. Whether a cure window nests inside a notice window. Whether an obligation is even in scope for the entity under review. These are functions. They take typed inputs, return typed verdicts, and they get unit tests.
  • Judgments about meaning. Does this paragraph express the same obligation as that one, in different words, under a different heading? No amount of code does this. This is the model's entire job.

On the engine I built this way, the first bucket came to roughly 150 tested functions. The model's scope narrowed to a single task — semantic matching between a extracted obligation and a template concept — and everything that determined an outcome lived in code a reviewer could read.

What the split buys

Auditability. A domain reviewer who disputes a verdict is pointed at a named function with a docstring and a test file, not at a paragraph of English that produced a different answer last Tuesday. This is the difference between a system a legal team will sign off on and one they won't.

Correctability. A wrong rule is a code change plus a regression test, and it stays fixed. A wrong prompt is a negotiation with a probability distribution — you tune it, the case passes, and you have no guarantee about the eleven cases that used to work. Every fix in the deterministic half is permanent; every fix in the model half needs a full eval run to confirm it didn't cost you something else.

Cost. Semantic matching on a short paragraph pair is a small call. Reasoning through an entire reconciliation is a large one. Narrowing the model's job shrinks the token bill by roughly the ratio of the work you moved into code, which on a 500-obligation document is not a rounding error.

Where to put the line

The test I use: try to write the rule down as a sentence with no hedging. If you can state it as "X wins over Y when Z," it belongs in code, and the fact that a model could also do it is irrelevant. If the honest statement of the rule contains "roughly," "in spirit," or "means the same thing as," it's semantic and it goes to the model.

The common mistake is putting the line too far toward the model because the rule feels fiddly to implement. Fiddly-to-implement is exactly the profile of a rule that will be applied inconsistently by a model and that nobody will notice is inconsistent.

Force structure at the tool-call layer

The seam between the two halves is where systems rot. If the model returns prose that your code parses, you own a parser, and that parser will meet an output shape it has never seen at the worst possible moment.

Give the model a schema and validate at the tool-call layer, so a mismatch triggers a model retry rather than landing in your code. This eliminates a whole category of glue and a whole category of 2 a.m. bugs. The deterministic half should never receive anything it didn't ask for by type.

The general form

This isn't a document-processing technique. It's the first architectural call I now make on any applied-LLM system: enumerate the decisions, sort them into statable and semantic, and let the sort dictate the architecture. The systems that get trusted in production are the ones where the model's authority is small, sharply bounded, and surrounded by code you can read.
