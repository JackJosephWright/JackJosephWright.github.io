Detecting stuck bots that report success

System
Three VMs running a game client plus a bot process, unattended overnight
Role
Sole engineer
Artifact
Node classifier, 5 states and ~14 sub-classes, 31 unit tests, gates by exit code
Finding
In every case the data needed to detect the stall was already in the logs. The detectors were reading the wrong signal.

The problem

A crash is easy. It leaves a stack trace, the process is gone, and a restart fixes it. The expensive failures on this fleet were the ones where the process was running, the logs were being written, and no games were being completed. Every health check returned green.

This is the list of those failures, what caused each one, and what the fix was.

The idle timeout that could never fire

The bot had an idle timeout: if nothing happened for long enough, abandon the game and recover. A node sat stuck for about seventeen minutes without it firing, and was eventually cleared by an unrelated external timeout.

"Nothing happened" was implemented as the log file stopped growing. The game client writes heartbeat and status traffic continuously, whether or not the game is advancing, so the log always grows. The idle timer reset on every check and the timeout could not fire.

Progress was redefined as a prompt actually handled, or the turn and phase counters advancing. One detail matters: when the turn state can't be read, that has to return "unknown" rather than "unchanged," because treating an unreadable state as progress reintroduces the same bug.

Two detectors feeding each other bad data

Some tools succeed by doing nothing on purpose — declining to activate an ability, skipping a stale phase. They send nothing to the game, so they produce no response traffic. But they were routed through the same confirmation mechanism as real actions, which waits for new engine traffic to prove the action landed.

No traffic arrived, because none should have. The confirmation timed out, the no-op was recorded as a suspected missed click, and it retried five times. Each retry counted as "a prompt handled," which fed the idle timer, which reset. One node logged 94 consecutive declines on the same prompt and never recovered.

Each mechanism was reasonable alone. Together they produced a bot that could not detect it was stuck. Genuine no-ops now finalize immediately and never enter the confirmation path.

The livelock: 2,089 consecutive reported successes

A confirmation click landed on Cancel instead of the confirm button, which rescinded the action. The engine re-issued the same prompt. The bot answered it the same way and hit Cancel again. This ran 2,089 times at roughly eight seconds per cycle, across several days, and every iteration logged success.

No detector fired, and each was behaving correctly by its own rules. The rescind is real engine traffic, so the log stayed fresh and the confirmation mechanism kept accepting each success. Every detector built to that point assumed a stuck bot goes quiet. This one was noisy.

The fix counts consecutive re-serves of the same prompt identity, using only distinct message ids so an internal retry isn't mistaken for the engine re-asking. Past five it stops trusting the reported success and records the interaction as unresolved so the metrics stop overstating. Past fifteen it abandons the game rather than riding a timer the rescind traffic keeps resetting.

Adversarial review of that fix caught a serious problem before it shipped. Prompt identity includes an id that is a static localization key, and one very common prompt type carries the same id all game. Without an exemption, five legitimate priority passes in one turn would have tripped the detector and fifteen would have conceded a healthy game.

The classifier

The classifier is split so the judgment is pure and testable. One function takes process count, log age, and a log tail, and returns a state plus evidence lines, with no I/O. A separate layer gathers that data over SSH. The pure half has 31 unit tests, including tests for precedence between states. The process exits non-zero when any node needs attention, so a scheduler can gate on it.

The five states are buckets. The work is in the fourteen or so sub-classes underneath, and nearly every one was added after it had already been missed once. Each carries a dated incident note in the source.

Three detectors that needed a second condition

DetectorWhy the obvious version didn't work
Stuck matchmaking "Awaiting match start" is normal between games. Flagging it alone raised a false alarm on a node that was actively playing. It only indicates a stall when the log has also gone stale.
Self-heal loop A bot stuck relaunching the client every ninety seconds keeps its log fresh and its process count correct, so it passes both the crash check and the staleness check while completing no games.
Modal loop An overlay guard clears a client-side dialog every cycle but the dialog never resolves. The activity keeps the log fresh, and the same code path suppresses the escalation that would otherwise fire. Caught by requiring the guard-clear count and a climbing idle counter together.

Alert volume is managed in both directions. Known-accepted fall-throughs are suppressed by an explicit allowlist, because one design-gated case was firing three times a night and would have buried real anomalies. In the other direction, a node that trips the slow-progress heuristic but is completing games gets downgraded to non-severe — some decks are legitimately slow. That required querying a wider window for completions than the window used for classification.

Error text parsed as data

The fleet probe counted running processes by parsing the output of a remote command. When SSH couldn't reach a host it printed a connection error to standard output, and that error contains the host's IP address. The leading octet parsed as a number.

An unreachable machine reported a process count of 100 and classified as the healthiest node on the fleet. The guard is one line. The general point is that a parser has to distinguish the channel carrying data from the same channel carrying an error.

Recovery when there is no supervisor

Navigation failures originally called exit, which is fine when something restarts the process and useless otherwise. A client update plus a stray browser window once killed every node for hours, and each manual restart died the same way within seconds.

Navigation failure no longer exits. It escalates: clear stray windows, relaunch the client, and on specific repeat counts invoke the launcher, because a plain relaunch can't clear an out-of-date-client screen. The escalation is capped, and backs off progressively — repeated fast reconnection attempts risk an account-level lock, so the recovery path needs to avoid causing a worse failure than the one it's clearing.

One recovery is destructive and is gated accordingly. A dead interactive desktop session can only be cleared by a reboot. That fires only on the specific evidence of a dead session, is rate-limited to one reboot per node per thirty minutes so a deeper fault can't become a reboot loop, and refuses to run if it doesn't know which deck configuration the node should restart with.

The same failure from inside and outside

A screen capture call had no timeout. On a degraded desktop the underlying system call blocks indefinitely, and one node sat inside a single capture for sixty-five minutes. Self-healing never triggered because nothing raised. Running the capture on a daemon thread with a fifteen-second join converts an indefinite hang into a catchable exception that existing recovery already handles. Fifteen seconds never trips a healthy capture, which completes in under a tenth of a second.

That is the same condition the classifier detects from across the network as a dead session. The watchdog stops one hung call from blocking the loop; a reboot is still what clears the underlying desktop.

Disk exhaustion from diagnostic screenshots

A node hit zero bytes free. Diagnostic screenshots alone held several gigabytes. That blinded screen capture, put navigation into a relaunch loop, and blocked the client updater, which needs substantial scratch space.

The fix was retention rather than taking fewer screenshots, since those screenshots are the evidence the validation process runs on: keep the newest N per category, prune the client's own logs, sweep periodically. Captured samples of prompts the system couldn't handle are excluded from pruning — those are the work queue, not diagnostics.

What these have in common

In every case above, the information needed to detect the problem was already being recorded — in the prompt, the turn counter, the retry count, the process table. The system was reading a different signal. The fixes that worked were redefinitions of what "progress" or "success" means, each shipped with a new detector class so the same gap can't reopen quietly.

The instruments now document their own biases. The phantom-click rate is recorded as a lower bound, because the game's own turn timer can advance a stuck game and satisfy the check. The stuck counter is documented as directional rather than exact. The liveness gate notes that crashes leave no record, so absence of data isn't evidence of health.

Three of the detector classes exist because a person watched the screen and saw a stalled bot while the sensor reported healthy. Watching for a few minutes found things that hours of aggregate metrics did not.
