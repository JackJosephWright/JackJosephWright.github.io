An LLM that plays Magic: The Gathering Arena

Status
Live. Playing unattended on a small VM fleet.
Result
49.1% over 55 games against Arena's built-in AI, at ~$0.03 per game
Role
Sole engineer
Repo

The problem is formally worse than it looks

Optimal play in Magic is at least as hard as the Halting Problem. You can embed an arbitrary Turing machine in a game of Magic such that the first player wins if and only if the machine halts (Churchill, Biderman & Herrick, 2021). The card pool is unbounded and grows every quarter.

None of that has to be solved, because the game client already did the hard part. Arena's rules engine computes the set of legal actions at every decision point and publishes it. So the undecidable problem becomes an enumerable one before the bot ever sees it. What's left is executing any option on that menu reliably, and choosing well among them.

That splits the work cleanly, and it gives the project its governing rule: cards are infinite, but interfaces are a catalog. A prompt shape — choose N, order the stack, assign damage — serves every card that ever uses it. Coverage is built against the interface, not the cards.

The game tells you almost everything, except where

The obvious approach to a game with no API is computer vision: screenshot the board, work out what's on it. That's what my previous attempt did, and it's what made it fragile.

Arena writes a log file that turns out to carry near-complete game state — effective power and toughness after all modifiers, what's tapped, abilities granted by other cards, who controls something versus who owns it, and an event stream covering every zone change, damage event and life change.

What it contains no trace of is screen position. Not a single coordinate. That one asymmetry decides the whole architecture: everything true comes from the log, and the vision layer shrinks to answering "where is this card on screen." Which is done by moving the cursor and reading which object the game reports under it — identity from the log, position from the cursor, mapping measured rather than guessed.

A click that reports success usually didn't

The hardest part of driving a game client is not clicking. It's knowing whether the click worked. The screen looks broadly the same either way, and a tool that returns "success" is only reporting that it didn't crash.

So no action counts as done when the tool says so. It counts as done when the game engine emits new traffic proving something happened. If that doesn't arrive within a deadline, the success is demoted, logged as a phantom, the screen is photographed, and the action retried. The deadline varies by prompt type — anything that waits on the opponent gets far longer — so the measurement reflects the bot's actuation rather than the opponent's thinking time.

The related trap: waiting for the interface to stop animating is not the same as waiting for it to be ready. One prompt arrives while the client is still showing a versus splash screen, which is perfectly still. The bot waited for stability, got it immediately, and clicked on the splash. That interaction failed on nearly every attempt for months before anyone worked out why.
