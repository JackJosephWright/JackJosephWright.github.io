Measuring what a Magic position is worth

Status
Offline measurement program. Deliberately not wired into the agent.
Role
Sole researcher and engineer
Method
Logistic regression fit by IRLS with L2 ridge; 5-fold grouped cross-validation, encodings cross-fitted inside each fold
Data
7 sets · 5,109,204 games · 31,407,915 card episodes (public 17lands replay exports)
Tests
137 unit tests across five modules

Question

An agent that plays Magic needs to know whether a move improved its position. That requires a value function over board states: given a frozen snapshot, what is the probability this player wins? The agent already ships a small eight-feature model over board geometry — life totals, creature counts, cards in hand, lands. The question this program set out to answer was whether knowing which cards are on the board beats knowing only the shape of it, and what the right representation of a board actually is.

The answers were mostly not the expected ones, and the most useful result was a hard ceiling rather than a gain.

Data handling

ConcernApproach
Volume ~3 GB gzipped, roughly ten times that decompressed, against a fixed disk allowance. Streamed over HTTPS and decompressed in memory; nothing decompressed ever touches disk. Only integer counts are checkpointed, so a dropped connection costs one set rather than a run.
Sampling Samples hash the draft identifier rather than taking the first N rows. The exports are chronological, so a head slice would train entirely on a set's opening days — when the format is unsolved and players are measurably worse.
Validation Five-fold, grouped by draft so no draft spans folds. Every card-level encoding is rebuilt inside each fold from training games only.
Shape The widest set's schema is 2,509 columns, carrying a fixed 30 turn indices per game regardless of actual length.

Leakage, and why sample size hides it

The obvious implementation builds the card-value encoding once over all data and then cross-validates the model. That leaks: the encoding has seen the validation games. Measured against the honest cross-fitted version, leakage inflated the headline result by about 25%.

The trap is that leakage severity scales inversely with sample size, which makes it nearly invisible during development. On the full dataset the leaky and honest numbers differ by a few thousandths. On a 399-game smoke fixture — the kind of thing used for a quick check — the same comparison read +0.334 leaky against −0.127 cross-fitted. The leaky version looked excellent; the honest version showed the features were actively harmful at that sample size. A pipeline validated only on small fixtures would ship the inversion.

Finding 1: a zone is a distribution, not an average

The single largest effect in the study came from changing no data at all. Card values aggregated as mean and max across two zones scored a Brier skill lift of +0.0133 over pure geometry. The same values, re-aggregated as sum, mean, max, min, spread, and known-count across three zones — adding the opponent's board — scored +0.0228. A 71% increase from parameterisation alone.

The reason is that a mean destroys the shape of a zone. One bomb among ten worthless tokens averages to mediocre. Sum carries total mass, max carries the spike, spread carries lopsidedness, and a known-count distinguishes "measurably weak" from "never observed" — which are entirely different states that a mean silently merges.

The corollary, tested separately: card values are additive to counts, never a replacement. Value distributions with the counts removed scored below plain geometry.

Finding 2: card face attributes cannot rank cards

If card quality could be read off rarity, mana value, and type, the whole problem would generalise to any card ever printed with no measurement needed. A leave-one-card-out study over 1,883 cards closed that escape hatch.

MeasureValue
Between-card win-rate variance that is real signal, not noise98.8%
Of that real variance, explained by rarity × mana value × type3.0%
Pairwise ranking accuracy from face attributes (chance = 50%)56.4%

Predicting every card at its turn-level average outright beats the bucket-based prediction. The buckets add noise, not signal. Within the same set, rarity, mana value and colour, cards spread a median of 6.5 percentage points and as much as 22.2 — two rares at the same cost and colour, identical on every face attribute, twenty-two points apart in win rate. Rarity itself is nearly flat and not even monotonic, because the deck a card appears in washes it out.

The correction: state the denominator

An earlier revision of this work reported that rarity, mana value and type recovered 93% of the signal — the opposite conclusion. Both numbers were arithmetically correct. The first was 93% of total outcome skill, in a model where card quality contributes only about 11% of the total; the second is 3% of card power. The first denominator makes any card feature look excellent, because most of the prediction comes from life totals and board counts regardless.

This is filed as a standing method trap rather than a one-off mistake: a percentage without its denominator is not a result. The published headline was corrected rather than quietly amended.

Finding 3: you cannot buy combat awareness with static state

The strongest result is a negative one. A value function was graded not on calibration but on whether the change in value across a transition recovers the realised value of a known-good action. Two actions, opposite outcomes:

ActionRealised gapShipped model+16 static features
Removal spell+6.3 pp29%120–126%
Attack+21 to +24 pp~31%~31%

Adding sixteen carefully chosen static features moved attack recovery not at all. Removal, by contrast, went from barely credited to fully credited — slightly over-credited, in fact.

The asymmetry has a clean explanation. Removal's entire value is written into the successor board: a creature is gone, and a static snapshot sees exactly that. An attack's value mostly is not — it lives in damage that will matter later, in the blocks the opponent now has to consider, in a race that has not resolved. A static position function is structurally blind to it, and no amount of additional static features fixes a representational gap. Either the transition itself gets priced, or the reasoning layer has to be told the rule.

Finding 4: the initiative asymmetry

One fitted coefficient turned out to be a finding on its own. A flag distinguishing "this snapshot is the end of my turn" from "the end of theirs" carries a large negative weight: all else exactly equal, the end of your own turn is a worse position than the end of your opponent's.

Which is obvious once stated — you are tapped out and it is about to be their move — and was invisible to every previous model because none of them recorded whose turn the snapshot came from. A related coefficient confirms the same channel: unspent mana on your own turn carries a negative weight.

Finding 5: the value function that teaches a bot to hoard

Card win-rate tables can be built conditioned on different events, and the choice of event is a choice of incentive.

Conditioned on holding a card, values rise with turn number — a card in hand on turn 10 correlates with winning more than the same card on turn 1. That is true as correlation and false as advice: still holding cards late means the game went long, which means you were probably ahead. A critic fed those values learns to hoard. Conditioning instead on casting the card removes the confound, because it conditions on having done something.

The same audit found the shipped model reads 0.184 for a perfectly even board on turn one, climbing toward even only around turn eighteen. That was originally logged as a calibration bug. It was reclassified as something worse: a miscalibrated display is misleading, but a miscalibrated value function that something optimises against is harmful.

The mechanism was then measured rather than assumed, and the first diagnosis was wrong. Attacking does not shrink the attacker's board — attackers end with more creatures than holders, on average. The defect is combat blindness specifically: a board-size critic prices an attack worth +13.5 points of realised win rate at +1.3. The shipped model's life-differential term recovers about 55% of it, so it under-rewards attacking by roughly half rather than teaching pure passivity.

Honest negatives

  • Two-turn trajectory features — the change in each quantity over the previous two turns — added +0.0003. Nothing. Level features already imply them.
  • A sorted-value vector replacing hand-picked aggregates scored a statistical tie on accuracy, so the aggregates leave no linearly recoverable information behind. It won on a different axis: its behaviour stayed linear across board strengths where the aggregates bent, misattributing where a card's value came from.
  • Graded against the snapshot population an agent actually stands in, the shipped model scores below the base rate. Refitting the same eight features fixes most of it, which means the deficiency is the fitted weights, not the feature set.
  • Marginal-value estimates computed by arithmetic on the fitted model rank plays correctly (per-card correlation ≈ 0.64) but over-promise levels by roughly a factor of two. Ranking is usable; the raw numbers are not calibrated gains and are not quoted as such.

Engineering: the out-of-memory bug

Two runs died silently in a fixed-memory container. The cause was a single expression in the Newton–Raphson fitter that scales the design matrix row-wise before forming the Hessian. That expression materialises a complete copy of the design matrix on every iteration — over a gigabyte per iteration, up to twenty-five iterations, on top of the matrix itself and the training slice.

Both the gradient and the Hessian are plain sums over rows, so both can be accumulated in chunks. Rewriting the fitter to accumulate over 250,000-row blocks dropped the largest temporary from roughly 1.26 GB to about 57 MB, a 22-fold reduction, with no change to the model. The fitter also gained a row mask so a training split is fit without materialising a copy of it at all.

Two details make this a fix rather than a patch. The chunked implementation was verified equivalent, not merely similar — coefficients agree with the single-shot form to within 1e-16. And per-fold peak memory is now printed on every fold line, for a specific reason: under a detached run an out-of-memory kill is indistinguishable from a clean exit, because the launching shell returns zero either way. The run has to carry the number that would explain its own death.

Known limitations

  • Train/serve skew, unresolved. The dataset identifies cards but carries no counters, auras, equipment, or disabling effects, so every stat feature is the printed value. A live agent observes modified values. Feeding live values into weights fit on printed ones is a distribution shift; feeding printed values is knowingly wrong on any modified board. This must be decided before any stat-bearing model is deployed.
  • Coverage. Card-value tables are built from a Limited format; median coverage of the agent's own Standard decks is under 20%, with several decks at zero.
  • Transfer is unmeasured, and the check reads as a false pass. Every recorded agent game so far is a loss, so a Brier score against a constant outcome collapses to a number that looks respectable while measuring nothing.
  • Not reproducible from this repository. The training script for the shipped weights lives in a predecessor codebase, so those weights cannot currently be regenerated. Every fix to the shipped model is blocked behind that.

Why none of it is wired in

The findings are deliberately not connected to the agent, and the reason is a design position rather than an unfinished task. Handing a language-model pilot a win-probability number and a table of card values risks reducing it to an executor of the statistical model — at which point the model may as well run alone. Any such feed is therefore introduced as a toggleable instrument, defaulted off, evaluated as its own experimental arm against a naive baseline, never quietly folded in.

The division of labour that came out of this program: the reasoning layer owns dynamics — rules, sequencing, tactics, the things it reads natively — and the measurement owns statics, what a frozen position is worth. A value is consumed as a difference at a decision point, never as a level. That requirement is why the models are graded on transition recovery rather than on calibration alone, and it is what surfaced the finding that static state cannot price an attack.
