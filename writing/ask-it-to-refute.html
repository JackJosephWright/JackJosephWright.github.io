Ask it to refute, not to check

Jack Wright · August 2026

Ask a model "is this finding real?" and it will agree with you. Ask it to refute the finding, instruct it to return refuted when uncertain, and the survivors are worth acting on.

The framing does the work. "Verify this" invites confirmation; the model's easiest path is to restate your claim with supporting detail. "Refute this, and default to refuted if you cannot establish it" inverts the burden of proof, and the difference in yield is not subtle:

  • On a generated candidate list, refute-by-default verification removed roughly 40% as unverifiable or wrong — before anyone spent human time on them.
  • On a code-review pass, about 29 raw findings became 8 confirmed. The other 21 were plausible, well-argued, and not real.

Why this matters more as generation gets cheaper

Generating 100 candidate findings is nearly free. Having a human read 100 findings is not, and the cost isn't only time: a list where a third of the entries are wrong trains its readers to stop trusting the list. One bad batch can end adoption of a system that is right most of the time.

Verification, not generation, is the throughput gate on anything that outputs candidates for humans. Budget accordingly — it is normal for the verification half of one of these pipelines to cost more than the half that does the actual work.

Make verifiers perspective-diverse, not redundant

The obvious scaling move is to run the same skeptic three times and take a majority. This is mostly wasted spend. Three identical skeptics catch one failure mode three times over, and they share every blind spot.

Give each verifier a different lens instead. On a code finding: one checks correctness, one checks security implications, one checks whether the reported behavior actually reproduces. Three lenses catch three classes of error, and disagreement between them is itself signal — it usually means the finding is real but described wrong.

Kill the finding when a majority refute. Keep the refutations attached to the survivors; a reviewer who can see the strongest argument against a finding evaluates it faster than one who only sees the case for it.

Calibrate before you trust any of it

None of this means anything without a graded set. Hand-grade 15–25 cases before the first real run, then report recall and false-positive rate as numbers. A pipeline at 92% recall and 0% false positives on a graded set is a claim you can defend. The same pipeline with no graded set is a feeling.

Include negative controls — items engineered to look like hits but that aren't. These catch the failure mode a naive answer key walks straight into, where every case in your key is a true positive and you learn nothing about the system's appetite for inventing them.

The trap: a rubric that can't see the deciding variable

The most expensive verification bug I've hit produced no false alarm at all. It produced a clean bill of health.

A strictness rubric scored both sides of a comparison 5/5 and rendered the row green. Underneath, the actual penalty figure had doubled. The rubric had no access to magnitudes — it could not be wrong, because it could only ever be irrelevant. It was answering a question adjacent to the one that mattered, in a confident voice.

When an assessment comes out clean, check whether the assessor could even see the thing that would have made it dirty. That question has found more real defects for me than any amount of prompt tuning.

And the root cause is usually upstream

In that same case, the assessors were not the problem. The extraction schema had no field for numeric values, so no figure ever reached them. Every hour spent improving the assessor prompt would have accomplished exactly nothing, because the information had already been discarded two stages earlier.

When a component gives bad output, the first question is not "how do I fix this component." It's "did this component ever receive what it needed?" In a multi-stage LLM pipeline the answer is no more often than you would expect.
