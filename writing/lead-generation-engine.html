Lead generation engine from public records

Status
Production, delivered
Role
Sole engineer
Stack
Python, public records ingest, commercial enrichment APIs, LLM verification
Tests
71

Problem

Target identification was manual and did not scale to a new territory. The requirement was a ranked list of qualified organizations with named contacts, each row carrying a rationale a salesperson could read before making a call.

Interface

InputPublic parcel and assessment records for the territory.
InputCampaign profile — qualification thresholds, geography, reference data.
OutputRanked target list. Organization, qualification evidence, buying-committee contacts, per-row rationale.
OutputLiving tracker. Upserts on re-run; human-entered columns preserved.

Pipeline

  1. Building spine. Filter parcel and assessment records to candidate structures.
  2. Firmographic match. Address-level join from parcel to occupying organization.
  3. Qualification. Multi-gate filter. Gates compile from the campaign profile.
  4. Enrichment. Buying-committee contact resolution against commercial APIs.
  5. Verification. Adversarial pass over every candidate. Refute-by-default.
  6. Rank and emit. Scored list written to the tracker.

Verification design

Candidates are checked by independent verifiers instructed to refute rather than confirm, returning refuted when evidence is insufficient. Verifiers are perspective-diverse rather than redundant — repeating one skeptic three times reproduces one blind spot three times.

MeasureValue
Candidates removed as wrong or unverifiable~40%

Funnel leakage audit

An audit of stage-to-stage counts identified a classification gate tuned too tightly, discarding qualified records before enrichment. Widening the gate recovered approximately 75 additional qualified leads — close to doubling the list. Every recovered record was passed through the same adversarial verification before delivery.

Detection method: conservation counts between adjacent stages. A stage that silently drops records is invisible without them.

Configuration refactor

Initial implementation was a script pile. It was restructured into a config-driven engine: typed records, gates compiled from configuration, source adapters behind one interface, a stage runner, and provenance manifests per run.

BeforeAfter
New market requires code changesNew market is a profile file plus reference data
No test coverage71 tests
Reruns recompute everythingExpensive stages persist structured output; reruns load and recompute deltas

Validation of the refactor: production output reproduced at zero API cost from persisted artifacts. The first preflight against a new market configuration failed on a genuine data gap rather than running on stale assumptions.

Delivery constraint

The output is a working surface, not a report. The tracker upserts on re-run and never overwrites human-entered columns, so sales annotations survive regeneration and feed the next pull's qualification.

Limitations

  • Coverage is bounded by public-record completeness and refresh cadence in the target jurisdiction.
  • Address-level firmographic matching degrades in multi-tenant buildings.
  • Enrichment is credit-metered; contact resolution is the cost driver per run.
  • Scale is county to territory, in the thousands of records.
